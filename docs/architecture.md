# Архитектура: исходные решения

Это проектные решения и критерии будущей реализации, а не описание готового кода. Сущности, стек и конкретная схема БД уточняются после списка функций и сведений о хостинге.

## Локальные данные

Интерфейс работает с локальным состоянием. Каждое изменение сохраняется в localStorage до отображения успешного результата. Ошибка записи, повреждение данных или переполнение хранилища показываются пользователю: приложение не сообщает об успешном сохранении, если его не было.

Версионированный локальный документ содержит данные, очередь ещё не подтверждённых операций, идентификатор устройства, номер схемы и сведения о последней синхронизации. Обновление данных и очереди выполняется одной записью документа. Между вкладками нужен механизм сериализации записей и уведомление об изменениях, чтобы вкладки не затирали друг друга.

localStorage привязан к браузеру и origin (протокол, домен, порт). Очистка данных браузера удаляет локальную копию; неподтверждённые облаком изменения при этом могут быть потеряны. Переезд на другой домен требует переноса данных. Локальный экспорт/импорт для резервного копирования — предложение для согласования.

## Офлайн-запуск

Service worker кэширует оболочку приложения и нужные ресурсы. После первого успешного открытия и завершения кэширования приложение должно открываться без сети. Самое первое открытие на новом устройстве требует интернета. Для домена требуется HTTPS.

Обновление оболочки не должно удалять локальные данные или очередь. Локальная схема имеет миграции, сохраняющие пользовательские записи.

## Синхронизация

У каждой сущности стабильный UUID; у операции отдельный UUID. Предусматриваются версия записи и отметка удаления. Удаления передаются как операции с отметкой, чтобы старое устройство не восстанавливало удалённые записи.

Синхронизация запускается при открытии, возврате в приложение, появлении сети, после изменений и при ручном повторе. Событие online — повод попробовать запрос, но не доказательство доступности Supabase. Ошибки обрабатываются с ограниченными повторами и увеличением задержки.

Сервер применяет операции идемпотентно и атомарно: повтор запроса после потерянного ответа не создаёт дублей. Клиент удаляет из очереди только подтверждённые операции и не теряет изменения, созданные во время запроса. Изменения сервера объединяются с локальными с учётом ещё не отправленных операций.

Для первого запуска на нескольких устройствах и конфликтующих правок требуется согласовать правило разрешения конфликтов. По умолчанию предлагается проверять серверную версию записи и сохранять обе версии конфликтующих изменений до выбора, вместо молчаливого затирания. Часы устройства не считаются надёжным источником порядка изменений.

Автоматическая синхронизация после восстановления сети гарантируется только при работающем приложении. При закрытом браузере она выполняется при следующем запуске; постоянная фоновая работа не предполагается.

## Доступ и будущее расширение

Нет экрана входа — согласованное требование первой версии. При этом владение доменом само по себе не ограничивает доступ к публичному приложению или Data API Supabase. Публичные политики чтения и записи личных данных не используются по умолчанию.

Способ ограничения доступа предстоит выбрать по возможностям хостинга: например, защищённый доступ к размещённому приложению и серверному API либо другое согласованное решение. Постоянный идентификатор владельца или устройства не является секретом и не заменяет проверку доступа. Anonymous Auth создаёт отдельные личности на устройствах и само по себе не решает доступ одного владельца с разных устройств.

Сущности и слой доступа предусматривают пространство владельца, чтобы позже можно было подключить Supabase Auth и политики RLS. При отсутствии согласованной защиты облачная запись не включается.

Публичный publishable key может использоваться только с соответствующими политиками доступа. Secret/service_role ключи остаются на сервере; их нельзя включать в браузерную сборку или localStorage. Конкретный серверный слой определяется после уточнения хостинга.

## Критерии проверки будущей реализации

1. Данные и очередь сохраняются после обновления страницы офлайн.
2. После кэширования оболочки приложение открывается без сети.
3. Создание, изменение и удаление офлайн после подключения отражаются в Supabase.
4. Обрыв запроса и потерянный ответ не приводят к дублям или потере очереди.
5. Изменения во время синхронизации остаются в очереди до подтверждения.
6. Удалённая запись не восстанавливается со старого устройства.
7. Конкурирующие изменения вкладок и устройств обрабатываются по согласованному правилу.
8. Ошибки localStorage и миграции проверяются без молчаливой потери данных.
9. Неавторизованный посетитель не получает доступа к личным облачным данным.
